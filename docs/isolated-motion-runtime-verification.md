# Isolated motion runtime verification

VS-024 adds observable browser evidence between a reviewed motion source plan and the verified stylesheet write.

The verifier answers one bounded question:

> Does the exact generated CSS region shown in this motion plan produce computed browser styles that agree with Afrodite's semantic motion compositor for the declared scenarios and sample times?

It does not execute target application modules, infer business state, or approve the source write.

## Flow

```text
motion UI IR + explicit CSS ownership
  -> server-generated CSS keyframe plan
  -> exact unified diff
  -> version-bound verification manifest
  -> sandbox="allow-scripts" preview-host
  -> static Shadow DOM fixture
  -> bounded trigger scenarios
  -> paused CSSAnimation samples
  -> computed styles and transform matrices
  -> comparison with semantic compositor
  -> server-recorded runtime evidence
  -> separate human plan approval
  -> compare-and-swap verified write or rollback
```

A motion patch cannot be applied until project bridge holds successful runtime evidence for the exact:

```text
planId
sourceVersion
CSS fingerprint
random plan challenge
scenario and sample set
```

Creating a new motion plan invalidates evidence from the previous plan.

## Verification manifest

Project bridge derives the manifest from its server-held source plan. The browser does not choose CSS text, selectors, sample budgets, or verification commands.

The manifest contains:

- one plan ID and stylesheet source version;
- the selected node and CSS Module class;
- up to eight explicitly managed clips;
- the exact generated Afrodite ownership region from the planned stylesheet;
- a deterministic fingerprint of that exact CSS region;
- a random per-plan challenge;
- bounded scenarios and sorted sample times.

The generated region is limited to 100,000 characters. The sandbox rejects external-resource and executable CSS constructs including `@import`, `url(...)`, `expression(...)`, `javascript:`, `behavior`, and `-moz-binding`.

## Isolated host

The motion verifier runs in the existing opaque-origin preview iframe:

```html
<iframe sandbox="allow-scripts">
```

It uses a dedicated protocol channel and a dedicated module entry. It does not use the React or Solid component registries and does not render the active project document.

For every request it creates its own closed Shadow DOM containing:

- one static focusable `div` fixture;
- one hidden expected-style probe;
- one `<style>` containing the exact generated CSS region;
- fixed baseline dimensions, opacity, transform, radius, and background.

The fixture and injected style are removed after the request.

## Trigger scenarios

VS-024 verifies source-supported triggers:

```text
mount
hover
focus
state with an explicit data-state value
```

Native pseudo-classes are converted only inside the isolated copy of the generated region:

```text
:hover -> [data-afrodite-verify-hover="true"]
:focus -> [data-afrodite-verify-focus="true"]
```

This makes activation deterministic without browser automation privileges or synthetic application event handlers. The exact source plan remains unchanged.

`data-state` is applied directly to the static fixture. The verifier does not create or test the application's state machine.

Manual and click triggers remain unpatchable because they would require invented JavaScript behavior.

## Sampling

Each same-trigger clip group receives a bounded sample set derived by project bridge:

```text
0
clip delay
clip delay + duration / 2
clip delay + duration * iterations
```

Times are deduplicated, sorted, and limited to twelve per scenario.

After a scenario is activated, the host obtains the fixture's CSS animations, pauses them, assigns each requested `currentTime`, waits for a browser frame, and captures:

- opacity;
- two-dimensional values from `matrix(...)` or `matrix3d(...)`;
- border radius;
- normalized computed background color;
- the number of active CSS animations.

The expected value is generated by `resolveMotionComposition` using the same clips and sample time.

## Comparison tolerances

Browser serialization and floating-point rounding are allowed within fixed bounds:

```text
opacity             0.02
matrix a/b/c/d      0.02
translation e/f     0.5 px
border radius       0.5 px
background color    exact normalized computed string
animation count     exact
```

Every sample stores expected and actual values plus structured differences.

## Server evidence boundary

Studio sends the sandbox result to project bridge. Bridge accepts it only when:

- the referenced motion plan still exists and has not expired;
- source version, CSS fingerprint, and challenge match the stored manifest;
- there are no runtime error diagnostics;
- the result contains the complete exact scenario/sample set with no duplicates;
- every sample is marked matched.

Bridge then issues an evidence ID associated with that stored motion plan. `/api/motion/apply` requires the evidence ID in addition to `planId + sourceVersion`.

The evidence requirement does not grant write authority to preview-host. The iframe has no project bridge token and cannot call the write route directly.

## Trust statement

Runtime evidence is observational verification, not cryptographic browser attestation.

A local process that already possesses the project bridge bearer token remains inside the human-controlled trust boundary and could manufacture requests. The challenge prevents stale or cross-plan evidence reuse; it does not prove the identity or integrity of a compromised local browser process.

The final safety boundary remains:

```text
explicit source ownership
+ exact human-reviewed diff
+ matching runtime evidence
+ plan/source-version approval
+ compare-and-swap
+ formatter/build verification
+ rollback
```

## Current boundary

- up to eight managed clips per motion source plan;
- scenarios currently group clips by the same exact trigger;
- combined mount plus hover/focus/state cascade verification is deferred;
- pseudo-class activation is deterministic attribute rewriting inside the sandbox rather than native pointer automation;
- colors are compared using browser-normalized computed strings;
- the verifier does not inspect screenshots, layout geometry, paint order, performance, accessibility, or reduced-motion behavior;
- evidence is process-memory state and expires with the motion plan or bridge restart;
- no Playwright browser matrix or cross-browser evidence exists yet;
- manual browser end-to-end verification remains outstanding.
